# Portfolio Presentation Standard

Agreed with the project owner on 27 October 2026. Apply this standard to future projects and use it when refreshing existing projects. It is a delivery requirement, not a claim that every older repository already complies.

## Required project story

Every project requires an introduction and business case explaining why it exists, the business problem, affected users, beneficiaries, alternatives considered, proposed solution, scope, expected value, measurable success criteria, risks and limitations. Use natural analyst prose and tables only when they clarify a comparison. Distinguish implemented features, planned work and measured results.

Include a beginning-to-end presentation, a user guide, architecture notes and process flowcharts. Use compact top-down Mermaid diagrams on GitHub, with readable labels and branches for actual decisions. Never fabricate functionality to fill a template.

## Repository and evidence

Save source to GitHub before deployment. Preserve agreed visibility. Use a private core and public showcase when proprietary source or actual data needs protection; a separate private repository is not automatically required for a public demonstration. Never publish private source just to make repositories look uniform.

Names use initial capitals for each ordinary word, preserving established acronym spelling. GitHub slugs use hyphens, for example `Inventory-Control-Tower` and `Meridian-Core`; display titles use spaces, for example `Meridian - Core`.

Use realistic simulated data and label it. Record tests actually run and their limits. Screenshots must show the actual application, exclude ChatGPT and private information, begin SS, and normally include only the three most informative views: SS1–SS3.

## Visual presentation

Use subtle editorial layouts: charcoal, white or warm grey, one restrained accent, strong readable typography and generous spacing. Prefer authentic interface evidence. Avoid glossy synthetic scenes, neon, exaggerated 3D effects, decorative robots and unsupported result claims. Use the same hierarchy and spacing across projects while keeping project-specific titles.

A cover is named SS0_Project_Thumbnail.png. Supporting captures are named SS1_Project_View.png through SS3_Project_View.png. Preserve editable source where practical. Prepare a table of upload fields, descriptions, skills, link, captions and image order for LinkedIn and Upwork.

## Handoff and completion

Provide a downloadable project folder with source, documentation and upload assets. Do not claim files were placed on the owner's computer unless the destination was actually accessible and the write verified.

Mark a project X only for its completed agreed demonstration scope. Use TO DO for remaining commitments, and explain any distinction between a completed demo and production readiness. Do not add projects beyond the seven agreed commitments; maintenance of completed portfolio work is allowed.
